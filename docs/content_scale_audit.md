## 2. 成就：三个层级的缺陷

### 2.1 缺陷一：进度覆盖断档（最严重）

里程碑不是"少"，是**全都挤在早期，后半程一条都没有**。

| 赛道 | 里程碑最远覆盖到 | 该模式总量 | 覆盖率 | 之后有多少关零成就 |
|---|---|---|---|---|
| 合成通关 | L300 | 700 | 43% | **400 关** |
| 停车通关 | 解锁 L20 | 800 | 2.5% | **780 关** |
| 合成章节 | 前 4 章 | 21 章 | 19% | **17 章** |
| 停车章节 | 0 条 | 22 章 | 0% | **22 章** |
| 3 星 | 30 星 | 2100 星（700×3） | 1.4% | **2070 星** |
| 停车 3 星 | 5 关 | 2400 星（800×3） | 0.2% | — |
| Boss | 0 条 | 56 只 | 0% | **56 只** |

玩家感受：打完前 300 关就没成就可拿了，最后 1180 关（78.7%）的推进只剩"解锁下一关"。

这些字段**代码里已经在算、已经在存、已经在 UI 展示**，却没有一条成就消费它：

| `dailyStreak` | 每日挑战连续通关天数 | — | **0** | 有 +50 金币奖励，无成就 |
| `dailyClearedDate` | 每日挑战首次通关 | — | **0** | — |
| `boosters` | 道具库存（加时/补卡/双倍） | 3 类 | **0** | 商店在卖 |

### 2.3 缺陷三：文案 / 判据不一致（已修 3 处）

## 3. 图鉴：50 不是数字问题

### 3.1 为什么"加到 100 款"不是答案

50 是 `VehicleType` 枚举的长度，每个条目 = 一张独立车模 PNG + 一条合成链档位。
加档位意味着：

1. 每加 1 款要出 1 张 1024×1024 车模（ImageGen → 去背 → 归一化 → 清灰底，见 MEMORY 工作流）
2. 合成链条 50 级已经让「顶级车」需要 2^49 张底牌才直接合出，实际靠牌堆权重抬档
3. ~~`tool/tint_variants.py` 的色相派生已把复用上限榨到 40/50，再往上只能新出图~~
   → 2026-10-21 已补齐最后 10 档（船舶 6 + 军舰 / 航母 + 直升机 / 无人机），
   现在 **50/50 全部有真车模**，色相派生的复用上限不再是约束（见第 6 节）。

所以图鉴的短板**不在条目数，在每条的厚度**。

### 3.2 真实缺陷：每款车只有「亮 / 不亮」二态

`_showDetail()`（`collection_screen.dart:268`）当前内容：
图 → 名称 → 车系 chip → 「第 N/50 号 · 已收集」→ 关闭按钮。

没有：首次点亮时间、累计合成次数、在哪些关卡当过目标、熟练度/奖牌、任何统计。

对比同类收集品的标准做法（每款 3 档熟练度徽章），当前深度约为标准做法的 1/4。

### 3.3 结构缺陷 A：15 款车型永远不当合成关卡目标

解析 `_handLevels`（70 关）+ 生成公式（`base = 20 + c*2.077 + group*0.25`，c=0..13 → 档位 20-49）：

- 手写段目标唯一档：**15 款**（1,3,4,12,13,22,23,24,39,40,44,45,46,48,49）
- 生成段目标档：**30 款**（20-49）
- 并集 **35 款**
- **永不当目标：15 款** —— bicycle / sedan / motorcycle / suv / van / ambulance / police / firetruck / limousine / bulldozer / crane / excavator / dumptruck / forklift / cementmixer

这 15 款只作为牌堆素材存在。作为"低阶素材"是合理的，但意味着：
**图鉴 50 格里，有 15 格（30%）从来没有一个关卡标题写着"去拿这辆车"。**

### 3.4 结构缺陷 B：手写段目标与章节叙事脱节

| 章节 | 标题 | 实际目标车 |
|---|---|---|
| 第一章 L1-10 | 街区起步 | taxi(3) / bus(4) / truck(12) / **highspeed(23)** |
| 第二章 L11-20 | 城市干线 | **rocket(44)** / highspeed(23) / subway(22) |
| 第三章 L21-30 | 轨道时代 | airliner(39) / subway(22) |
| 第四章 L31-40 | 天空征途 | spaceShuttle(45) / fighter(40) |
| 第五章 L41-50 | 星际探索 | spaceShuttle(45) ×6 |
| 第六章 L51-60 | 星港试炼 | **warpShip(49)** / maglev(24) |
| 第七章 L61-70 | 机关极限 | highspeed(23) / airliner(39) / rocket(44) |

第一章第 5 关就在打高铁、第二章就出现火箭，第五章连续 6 关同一辆航天飞机。
"街区起步"的叙事和实际目标车完全对不上，也是图鉴前期推进忽快忽慢（3.5 关/款 → 22.5 关/款）的来源。

### 3.5 结构缺陷 C：停车 22 章只用了 18 款，且有 4 章是"换名不换车"

| 车型 | 出现章数 |
|---|---|
| `warpShip` | 3（第 14 章星际港口 / 第 18 章曲速航道 / 第 22 章反重力区） |
| `starship` | 3（第 17 章彗星轨道 / 第 19 章悬浮城 / 第 21 章机甲工厂） |
| 其余 16 款 | 各 1 章 |

第 19 章「悬浮城」、第 21 章「机甲工厂」、第 22 章「反重力区」的标题和副标题都换了，
但棋盘上的车、章节图标、目标车全是同一张 PNG。

**零成本修法**：`VehicleType` 里还有 32 款没被停车用过
（motorcycle / suv / van / ambulance / police / firetruck / limousine / bulldozer / crane /
excavator / dumptruck / forklift / cementmixer / dinghy / fishing / ferry / sailboat /
speedboat / barge / carrier / glider / helicopter / drone / cargo / seaplane / stealth 等），
直接换 4 个 `ParkingChapter` 的 `tier` 即可，不需要任何新美术。

## 4. 关卡数量与内容密度的错配

1500 关本身没问题（合成 700 已验证 slack 曲线在心流通道内，停车 800 已全量可解性回归）。
问题在于**每一关能给玩家的"新东西"密度**：

| 维度 | 1500 关能提供的新内容 |
|---|---|
| 车型 | 50 款（每 30 关 1 款，后期 22.5 关 1 款） |
| 章节 | 43 章（每 35 关 1 章） |
| Boss | 56 只（仅合成，每 12.5 关 1 只） |
| 成就 | 27 条（前 300 关内基本全部触发完） |
| 图鉴奖励 | 1 个终局大奖（50/50，500 🪙） |

成就 27 条要服务 1500 关，等于**每 55 关 1 条**；而市面同类消除游戏的成就密度通常在
**每 5-8 关 1 条**（含章节、连击、技巧类）。当前密度的 1/7 ~ 1/10。

## 5. 修复方案

### 方案 A：成就扩展 27 → 67（推荐先做）

纯数据 + UI 改动，零新美术，全部可单测。

| 分组 | 目标条数 | 组合方式 |
|---|---|---|
| 通关里程碑 | 8 | 现有 6 + 补 500 / 700（现 clear_all） |
| 章节通关 | 21 | **按 `levelChapters` 循环生成**，每章 1 条（替代硬编码的 chapter_1/4） |
| Boss | 6 | 首杀 / 5 只 / 15 只 / 30 只 / 56 只全徽章 / 单章 4 连杀 |
| 停车 | 10 | 现有 6 + 每 5 章 1 条（22 章 → 4 条） |
| 收集 | 8 | 6 车系各 1 + 全 50 + Boss 徽章墙 |
| 技巧 | 6 | 连消 5/10/15 + 3 星 100/500/2100 |
| 生活 | 8 | 签到 30/100 + 金币 5000/10000 + 每日连胜 7/30 + 每日首通 |
| **合计** | **67** | 密度提升到每 22 关 1 条 |

配套改动：
1. `Achievement` 加 `group` 字段（枚举 7 组）+ `achievements_screen` 分组渲染 + 顶部「进行中 / 已完成」筛选
2. 章节成就用生成器构造，不再一条条手写（避免再出现 L1-40 这种硬编码漏改）
3. 新增 `test/achievement_coverage_test.dart`：断言 id 唯一、每章都有成就、无硬编码的车型/关卡总数文案、成就不重复奖励

### 方案 B：图鉴加深度轴（第二轮）

1. **熟练度**：`PlayerData.producedCounts: Map<int,int>`（合成产出计数）→ 每款车铜 10 / 银 50 / 金 200 三档奖牌
   → 图鉴格子角标显示奖牌，50 款 × 3 = **150 枚可收集**
2. 详情抽屉补：首次点亮日期、累计合成次数、作为目标的关卡数
3. 图鉴大奖从"单一 50/50 终局"改为"6 车系小奖 + 全收集大奖"，避免中后期只有一次正反馈

### 方案 C：停车章节换车（零成本，可与 A 并行）

把第 18/19/21/22 章的 `ParkingChapter.tier` 从 warpShip/starship 换成 4 款未使用的车型
（如 `firetruck` / `bulldozer` / `ferry` / `drone`），标题与副标题同步改。
不新增美术、不改生成器、不改难度曲线，只需重跑 `parking_solvability_full_test`。

### 不建议现在做

**扩档位 50 → 70**：需要 20 张新车模（ImageGen + 去背 + 归一化 + 清灰底 + mini 端 256px 副本），
且合成链条变长会拉动牌堆/难度全套参数重标定。收益（图鉴多 20 格）远小于成本。

## 8. 车模补齐：17 → 40 → 50（2026-10-21）

### 8.1 为什么必须补

合成牌堆的刷车范围是 `0 .. targetTier.index-1`，高关卡会一路刷到
`warship / carrier / helicopter / drone`。这些档位原先 `sprite == null`，
在棋盘卡面、图鉴、停车目标车上全部回退 emoji —— 而 Web 端 CanvasKit
不加载系统 emoji 字体，实际显示是**豆腐块**。「看不见车」的投诉有一半来自这里。

### 8.3 踩坑：白帆被去背算法切成筛子

`remove_bg.py` 用「与背景色的色距」判透明。白色/米色帆布与白底 RGB 几乎相同，
色距 < T1 → 整片判为背景，只在有缝线的地方留下不透明碎块。第一版白帆、
第二版米色帆都成了「网格骨架」，深色卡上是破帆。

三个版本后才收敛：**帆布改用深藏蓝（高饱和）**，色距远，去背干净。
同时新增 `tool/polish_sprites.py` 兜底：

1. **内部空洞回填** —— `remove_bg` 把背景像素设成 `(r,g,b,0)` 时保留了 RGB，
   所以被吃掉的浅色区域还能救。从四边 flood fill 标记「真外部背景」，
   剩下的透明像素就是封闭空洞，恢复 alpha=255（跳过 `(0,0,0,0)` 水印区）。
2. **丢弃游离碎块** —— 只保留最大连通域 + ≥ 其 3% 面积的次级块，
   清掉直升机上方的杂点。

## 9. 车模降采样 1024 → 512（2026-10-21）

### 9.1 为什么 1024 是纯浪费

游戏里车模的最大显示尺寸：

| 位置 | 逻辑尺寸 | 3x 屏实际像素 |
|---|---|---|
| 图鉴详情大图 | ~180 | 540 |
| 图鉴格子 | ~90 | 270 |
| 棋盘卡面内部 | 格子 96 × 1.42 ≈ 136 | 408 |
| 停车车身（长边） | ~200 | 600 |
| `VehicleSprites` 解码宽 | `targetWidth = 384` | — |

最大需求约 600px，且 `VehicleSprites` 本来就按 384 解码。1024 原图对运行时**零收益**，
只多占包体和安装体积（iOS/Android 都计入）。

### 9.2 结果

50 张统一 LANCZOS 降到 512×512 RGBA（保留 alpha 与 `optimize=True`）：

- `assets/vehicles` **18.4MB → 5.1MB（-72%）**，单张均值 368KB → 102KB。
- 内容占比不变：旧版 bbox 对角线 920/1024 = 0.898，新版 460/512 = 0.898，
  各车型之间的视觉体量关系完全保持（不需要重新调 `_fillW / _fillH / 1.42` 等参数）。
- 512 在 44px 棋盘格 / 90px 图鉴格下与 1024 无可辨差异（已按实际尺寸 2 倍放大目视比对）。

### 9.3 防回退

`tool/normalize_assets.py` 的 `CANVAS` 改成 512、`TARGET_DIAG` 改成 460 ——
**否则下次补车型重跑归一化，会把 512 重新拉回 1024**（放大后还是糊的，且体积翻四倍）。

原始 1024 处理产物备份在 `/tmp/vehicles_1024/`（临时目录，非仓库）；
`generated-images/` 里的白底源图仍是 1024，需要更大分辨率时可从源图重跑处理链。
